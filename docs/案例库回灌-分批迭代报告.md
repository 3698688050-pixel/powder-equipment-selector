## 3. 回灌的三层结构

1. **设备库层**（`index.html` 的 `DATA`/`DATA_MATERIALS`）：48 台设备、1433 条物料，未改动结构。

## 4. v7 打分：九项 + 门控 + 每条规则的案例依据

`total = Σ W·term`，项含义与 v6 方案一致（A 粒度 / B 产能 / C 机理 / D 粉碎比 / E 特性 / F 物料行业先验 /
G 工艺链 / H 分级精度 / **P 案例先验**）。

### 4.1 权重（`tools/fit.js` 的 `W`）

```
A .281  B .187  C .140  D .082  E .077  F .039  G .026  H .051  P .117
```

> 这是 v7.1 的权重（修掉 §10.1 的行业后缀 bug 之后重搜的）。v7 原值是
> `A .248 B .187 C .155 D .135 E .068 F .034 G .023 H .046 P .104`；特征一修，
> D（粉碎比）就从 .135 掉到 .082 —— 因为过去 99 例的物料大类全都退化成 `other`，
> 「粉碎比」项反而被迫承担了一部分本来该由行业先验承担的分辨力。

来源与约束：

- 目标函数**只用留一（CN）+ 跨站（EN）**，样本内不参与选参：
  `score = 留一Top3 + 跨站Top3 + 0.5×(留一Top1 + 跨站Top1)`。
- 粗网格 576 组（`node tools/fit.js --tune`）的最优解是 `A.271 B.167 C.146 D.146`：落在 `C≈D` 的并列边界上，
  与 v6 定下的相对序 `A 粒度 ≥ B 产能 ≥ C 机理 > D 粉碎比` 冲突，目标函数 213.5。
  加约束后细搜 672 组（`node tools/tune2.js`）得到上面这组，目标函数 **213.9**——
  **约束不是妥协，是顺带找到了更好的解**（留一 Top1 57.1→56.4 略降，跨站 Top1 60.9→62.5 涨回来）。
- 相对序的依据：粒度/产能几乎每例都能查到（证据强）；机理只有"机械磨/气流磨"这种粗标签（次强）；
  粉碎比依赖入料粒度字段，99 例里有相当比例缺失（最弱）。P 案例先验放在 E/F 之后，因为它是**统计外推，不是物理量**。

### 4.2 门控（`GATE`）：只保留物理上说不通的组合

| 规则 | 参数 | 案例依据 |
|---|---|---|
| 实验机产能上限 | 30 kg/h | 标注"实验室"的 7 例，最大 10kg/h；工业需求下推实验机是明显错误 |
| 工业机产能下限 | 5 kg/h（分级机豁免） | 最小案例 0.5kg/h（分级线），工业机做不到 |
| 分级机不适用 | 入料 ≥160μm **且** 粉碎比 ≥3 | 40 例标注"分级"的案例，入料上限 154μm（都是已经磨过的粉）；而标注机械磨/球磨的"超细水泥"那几例入料是 mm 级、必须真磨 |
| 无需粉碎 | 粉碎比 ≤1.35 且非打散型 | 打散/团聚还原（涡流磨、转子磨、蜂巢磨、改性机）在粉碎比 <1.35 时依然成立，其余磨机没有意义 |

**被案例证伪并回滚的规则**（重要）：

- v6 曾写"分级机不接粉碎比 ≥3 的活，一律出池"。回灌后发现标注"分级"的案例里 **11 例粉碎比 ≥3**——
  物料本身就细，分级只是切分布。孤立看"粉碎比"是错的判据，必须结合**入料绝对粒度**。
  A/B（最终权重下）：仅粉碎比≥3 → 留一 54.0/74.8、跨站 60.9/79.7；加上入料≥160μm → **56.4/74.8、62.5/79.7**。

### 4.3 口径修正（指标中性，但必须修）

1. **成品粒度基准换算**：案例成品常标 D50/D90/D95/D99，直接和设备 D97 范围比会系统性偏细。
   统一换算到 D97 当量（D50 ×2.5、D90/D95 ×1.2、D99/D100 ×0.9）。指标不变（因为 A 项本来会在多种范围里取最优），
   但口径必须对齐，否则"9μm D50"和"9μm D97"被当成同一件事。
2. **伪型号过滤**：`手册原文`/`系列覆盖 X~Y`/`未列`/`可调` 这类不是型号名。当成单一型号会按"利用率"打分：
   蒸汽动能磨 `系列覆盖2000~20000kg/h`，5000kg/h 落在 25% 处被扣成 B=0.75。改为**产品线带宽语义**（带内即满分，越界才扣）。
3. **产能脏值过滤**：产能字段里混粒度（`分级产能D97:15μm:2.7/4.0/5.4`）或斜杠并列值时不做型号级解析，
   否则把 `D97:15μm` 算成 97000kg/h（球磨线碳酸钙/石英方案曾解析出几十条垃圾产能区间）。

### 4.4 两条由案例支撑的加减分

- **气流磨在大产能上做经济性折减**（`cap ≥ 3000 kg/h` 时 `B ×0.9`）：
  19 例 ≥3t/h 的案例里只有 **1 例**走气流磨（磷酸氢钙 3000kg/h），3 例走蒸汽动能磨（手册原文"超细化低成本生产"）。
  压缩空气成本随处理量线性上涨，这是能量成本差异，不是可行性差异，所以只折一档不设门。
  A/B：折减后留一 Top1 55.8→56.4、跨站 60.9→62.5。
- **族级兜底的区间再向外放一档**（÷1.6 / ×1.6）：薄族（蒸汽 5 例、球磨线 7 例）样本窄，不收窄就会把合理工况判成越界。
  指标不变，作为稳健性保留。
- **同型号联合校验**：`capModels` 与 `sizeModels` 同时存在时按型号名前缀配对（`FL200↔FL600`），
  取 `W.A·a + W.B·b` 联合最大，避免"最大产能机 + 最细粒度机"拼成一台不存在的设备。指标不变，属正确性修正。

## 5. 为什么"Top3 100%"不可能达到

三条独立证据：

1. **标注是多对一的。** 12 例多标签（球磨线+分级 6 例、改性+机械磨 5 例…）；同一个工况，
   ALPA 可能卖整线也可能只卖主机，标签记的是**成交内容**而不是**唯一最优解**。
2. **离线先验再强也上不去。** `node tools/frontier.js` 扫 P 权重（案例先验）0.05→0.90：
   样本内 Top1 最高只到 **70.7%**（P=0.189）就饱和，再加大 P 会因为把所有案例都判给高频族而崩溃
   （P=0.9 时 Top1 掉到 63.6%、留一 Top3 掉到 54.6%）。**没有任何参数能让 Top1 接近 100%。**
3. **残差归因（21 例未进 Top3 的逐例核查，`data/replay-cn99.tsv` 的 `cause` 列）**：
   排序问题 17 例（标注族已进 Top3 只是不是第一）、族边界 16 例、规则冲突 4 例、数据缺口 1 例。
   族边界里最典型的是"分级 vs 磨+分级"：分级机在物理上也能达成那个粒度，ALPA 卖的是磨机线——
   **工况输入无法区分商业选择**，只能靠 P 先验压一点。

所以本文所有指标都写明 Top1/Top3 两个数，并区分"样本内/留一/跨站"，不合并成一个数字。

## 6. 批次 4 的残差（37.5% / 45.8%）

批次 4（例 76–99）是全 4 批最差，24 例里 10 例未中 Top1。逐例看：

| 类型 | 例数 | 典型 |
|---|---|---|
| 蒸汽族数据缺口 | 3 | 滑石粉、粉煤灰×2 标注蒸汽，实际推气流磨/振动磨。`蒸汽动能磨` 的 `size="—"`、`cap="系列覆盖2000~20000kg/h级产能(手册原文)"`，型号级解析为空，A/B 只能走族级兜底 + 未知折减 |
| 分级 vs 磨+分级 | 5 | 超细水泥×2、重晶石、磷酸氢钙、金属粉末：feed 已 ≤160μm，物理上分级也成立，ALPA 卖的是磨机线 |
| 改性线判给分级 | 2 | 粉煤灰改性、广东改性：改性机只在 `materials` 里挂了非金属矿填料，没挂粉煤灰 |
| 排序差一名 | 2 | 标注族在 Top2 |
| 命中 | 12 | |

**没有继续调参去压这 10 例**，理由：

- 继续用留一/跨站指标选参，已经从"验证"变成"拟合"，指标会虚高；
- 蒸汽族的根因是**设备数据缺失**（手册没有系列粒度/产能），补数据才是正解，不是调权重；
- "分级 vs 磨+分级"的根因是**商业选择不可从工况推导**，无论怎么调都会在另一批案例上还回去。

## 7. 案例检索层（页面上的"参考成交案例"）

位置：`index.html` 结果区下方（`__CASE_KB_LOGIC` 区间，源码在 `tools/case-module.js`，用
`node tools/inject-case-module.js` 注入，幂等）。

打分距离（`MAT_W = 1.5`）：

```
dist = 1.5·dMat + min(0.9·dSize, 1.5) + min(0.35·dCap, 1.2) + min(0.25·dRatio, 1.0)
```

- `dMat ∈ {0, 0.4, 1}`：同物料 / 同物料类别（物料库 `cat` 相同）/ 不同。
- `dSize`、`dCap` 用对数距离（`|ln(a/b)|`），粒度先换算到 D97 当量。
- **物料不一致的代价（1.5）大于其余三项惩罚之和的上限**，否则会拿"粒度产能刚好相近的别家物料案例"当近邻
  （实测把 磷酸铁锂 500kg/h D97 9μm 判给"锡粉 1000kg/h 7.54μm"的案例）。改乘性/加大系数后回到正确近邻。

UI 上给出：5 个最相近的真实项目（含"相近点：同物料/粒度相当/产能相当"），以及"案例佐证"——
最近 20 例里与该 Top-N 设备族一致的计数。**并明确写着"这是 1:1 最近邻匹配，证明的是案例能被找回，
不等于设备排序全对"**，避免把检索命中率误读成选型准确率。

## 8. 兼容性与风险边界

- **不改主选型公式**：`evaluate()`/`pickModel()` 未改动，页面行为只在结果区多了"参考成交案例"区块（只读）。
  `index.html` 增加约 140 行，全部落在两个标记区间内，可用脚本重生成。
- **权重没有上线**：v7 九项权重与门控只在 `tools/fit.js` 里，属于离线评估结果，等工程师复核再决定是否替换页面公式。
- **样本偏差**：成交案例 ≠ 唯一最优解（能卖出去的方案受价格、交期、既有产线影响）。
- **超范围输入不保证**：大产能 >3t/h、超细 <2μm 的样本各只有个位数，这两类结论必须工程师复核；
  页面上所有案例卡片都带"资料待确认"口径。
- **中英文未合并去重**：两站案例按站分别计数，跨站指标（EN 64 例）用的是"只在中文案例里检索/取先验"，
  所以中文独有的族（球磨线）在跨站指标里天然吃亏，这是口径使然而非缺陷。

## 9. 复算方式

```bash
node tools/fit.js                    # 样本内 / 留一 / 跨站 三行指标
node tools/fit.js --batch 4          # 单批指标 + 未命中清单

node tools/match-case.js             # 案例检索层指标（自匹配/留一/投票/跨站）
node tools/match-case.js 磷酸铁锂 500 D97:9 80   # 手动查一个工况的 5 个最近邻
node tools/replay-report.js --write  # 逐例回放表 → data/replay-cn99.tsv
node tools/build-cases-embed.js      # 重建 index.html 里的 DATA_CASES（--check 只校验）
node tools/inject-case-module.js     # 把 tools/case-module.js 注入 index.html（--check 只校验）
node tools/build-engine-embed.js     # 把 tools/kb.js+fit.js 打包注入 index.html（--check 只校验）
node tools/dump-offline.js           # 导出 CN 99 例的离线 Top3 → C:/tmp/offline.json（页面逐例对齐用）
```

A/B 开关（只用于复现本文的对比行，不参与默认行为）：

```bash

NOBIG=1   node tools/fit.js          # 关掉气流磨大产能经济性折减

```

## 10. 页面与离线同一份 `score()`（v7.1）

§3 当时写的是"主选型的 `evaluate()` 一行没动"。这一节是那个决定的收尾：**页面现在也跑 v7**，
但跑的不是复制粘贴的第二份公式，而是把 `tools/kb.js` + `tools/fit.js` 源码原样打包进页面。

### 10.1 先修了一个数据 bug（页面对齐时发现）

做页面/离线逐例对齐时，两边的 Top3 大面积不一致。根因不在打分，在案例读取：

```
中文站行业列是 "电池材料应用案例" / "非金属矿应用案例" …
kb.js 里 IND2CLASS 的键是 "电池材料" / "非金属矿" …
→ MATCL(ind) 全部返回 'other'
→ 先验的「物料大类」这一级（full / kr / k 三个分格）在 99 例里退化成同一个格子
```

英文站行业列是干净的（`dry-grinding`、`battery-materials`…），所以只有中文侧被静默打坏。
这种 bug 的可怕之处是**指标不会报警**：修之前样本内 61.6/78.8，修之后 65.7/80.8（涨了）；
而留一/跨站反而略降（56.4/74.8 → 55.8/76.7、62.5/79.7 → 56.3/79.7）——
坏特征让「粉碎比」项替行业先验分担了一部分分辨率，这在小样本上会显得泛化更好。

处理方式：**不改回坏特征，而是重调权重**。`node tools/tune2.js`（目标只用留一 + 跨站，672 组、
仍守 `A≥B≥C>D`）给出 §4.1 的 v7.1 权重，留一 Top3 从 73.0 抬回 76.7、样本内 65.7/80.8。

### 10.2 注入方式与三个坑

`node tools/build-engine-embed.js` 把两个文件塞进两个函数作用域 + 一个最小 CJS shim
（`process={env:{}}`、`require` 只认 `fs`/`path` 桩），`kb.js` 用页面已有的
`_DOM={DATA,DATA_MATERIALS,CAT_ALIAS,SWITCH_TAG,TAG_SWITCH,DATA_CASES}` 取代文件读取，
最后暴露 `window.POWDER_ENGINE = {K, F, W, GATE, CAT2IND, TRAIN, PRIOR, makeCtx, rank}`。

踩过的三个坑，都写进脚本注释了：

| 坑 | 症状 | 处理 |
|---|---|---|
| 注入锚点在 `const DATA_CASES` **之前** | `ReferenceError: DATA_CASES is not defined`，整个 `<script>` 中止 | 锚点改成 `/* ==CASE_KB_LOGIC_END== */`（案例库之后），且注入前用 `lastIndexOf` 自愈摘旧块 |
| 写回把 CRLF 归一成 LF | `git diff` 整文件重写（2640 → 3474 个 CRLF 全变） | 写回统一 `norm(html).replace(/\n/g,'\r\n')`；`tools/*.js` 保持 LF |
| 粉碎比用 D97 当量算 | 页面 Top3 与离线系统性错位 | `makeCtx` 的 `ratio` 用**原始**成品粒度：`feed / rawSize`，与 `fit.js` 的 `ctxOf()` 同口径 |
| 三个注入脚本的执行顺序 | `inject-case-module.js` 重写「案例逻辑块」区间时会连带吃掉引擎块（引擎就在该区间的尾部） | 顺序固定为 `build-cases-embed` → `inject-case-module` → `build-engine-embed`；每个脚本跑完都跑一次 `--check` |

页面侧新增的输入只有「入料粒度（可选）」一个：不给就 `ratio=null`，粉碎比项与分级门控都不触发（中性先验）。

### 10.3 同一性证据：99/99 逐例同序

```bash
node tools/dump-offline.js                 # 离线侧 → C:/tmp/offline.json
ego-browser nodejs < round-11.mjs          # 页面内直接调 POWDER_ENGINE.rank 复算同 99 例
# 比对：页面(引擎直调)/离线 Top3 逐例一致 99/99
```

**同一个输入 → 同一个排序**，这条通路是严格一致的（差异 0 例）。

而走完整 UI 交互（物料名自动归类 → 类别 → 打分 → 渲染卡片）时会掉到 **61.6/77.8**。
逐例 diff 是 7 例翻转（DOM 多命中 2 例、少命中 5 例），净差 3 例，原因两类，**都不是引擎不一致**：

| 原因 | 可见例 | 机制 |
|---|---|---|
| UI 物料类别 ≠ 案例行业（大类都不同） | 中国科学院三合一（chem vs 高新材料→other）、成都单晶三元（other vs 电池材料）、山东黄原胶（other vs 精细化工） | 大类一变，先验的 `k` 分格和 F 项跟着变；离线用的是案例自己的行业列，线上只有用户选的类别 |
| 页面上特性标签默认一个都不选 | 深圳三合一实验室（Top3 掉到全分级） | E 项（特性，权重 .077）落空；离线侧用 `caseTags()` 从物料库补出 heat/sticky 之类的标签 |

换句话说：**离线口径拿的是「最理想输入」，线上拿不到其中一部分**，这层差值约 3pp Top3。
要消掉它只能让用户直接选行业、再逐个勾特性标签——表单会重很多，不值。

（附带一条方法论提醒：按「UI 类别与案例行业是否同大类」分组解释不了差异——
吻合 50 例 Top3 76.0%、不吻合 49 例 79.6%，差异被别的原因抵消了。分组看着合理，但不是结论。）

### 10.4 与 §5 一致：不承诺 Top3 100%

页面口径下仍然坚持 §5 的三条证据：案例标注是多对一的（一个工况可以同时标"机械磨"和"气流磨"）、
99 例里 40 例分级案例的入料是已经磨过的粉（154μm）、蒸汽族/球磨线在中文站才有。
**能承诺的是"已知案例 100% 可被检索层找回"（自匹配恒为 100%）**，Top3 命中做不到也不该做到 100%。
